You can now leave one conversation looping, keep another on recovery only and switch a third off

This release also fixes the settings namespace collision from #64, brings old settings into the active profile and includes the dependency updates from #66

## A mode for each conversation

The control beside the message input now applies to that conversation ([#67](https://github.com/HsiangNianian/dsh-auto-continue/issues/67), [#68](https://github.com/HsiangNianian/dsh-auto-continue/pull/68))

| Mode | What it does |
| --- | --- |
| Follow default | Uses the profile's default session mode |
| Off | Stops automatic followups and excludes this conversation from the loop guard |
| Recovery only | Recovers eligible failures and silent turns, leaving normal completions alone |
| Autonomous loop | Also continues after normally completed turns |

- Choices are saved on the host, survive restarts and sync across tabs
- **Enable auto-continue globally** remains in the plugin settings and pauses automatic followups without replacing individual choices
- **Default session mode** controls conversations using Follow default, with Recovery only as the initial default
- Switching Off cancels queued grace, cooldown and loop-guard retries but leaves a running turn alone
- Switching from Autonomous loop to Recovery only cancels pending autonomous followups, and turning a mode back on does not revive cancelled sends
- **Resume now** still requests one manual followup while paused or Off without changing the saved mode

Your existing global pause and loop preferences carry over, and conversations without an override follow that default

The loop guard still has its own global setting and remains independent of global pause, while a conversation set to Off is excluded from it

## Settings save and migration fixes

Hosts exposing both legacy and profile settings APIs could register auto-continue twice and reject saves with `settings/conflict`, as reported in [#64](https://github.com/HsiangNianian/dsh-auto-continue/issues/64)

[#65](https://github.com/HsiangNianian/dsh-auto-continue/pull/65) keeps the profile configuration as the single settings owner on these hosts and imports the old auto-continue section from `$DSH_HOME/settings-legacy.yaml` when needed

- Imports happen once per profile, preserving old pause settings and custom prompts without overwriting explicit profile values or edits made during the import
- The original legacy file and other plugins' settings are left untouched
- A completed import stays completed after a full settings reset, so old values do not come back unexpectedly
- Automatic recovery and the loop guard wait while a required import is pending or fails, keeping saved pause choices from being bypassed
- Hosts with nothing to import do not wait for a settings editor
- YAML diagnostics no longer include source snippets that could expose unrelated settings, and the bundled parser keeps its ISC license notice

- Type checking, build, the full regression suite and the pinned DSH plugin checker
- Settings and compatibility checks against published DSH `0.1.7-rc.2`, `0.2.0-rc.1`, `0.2.1-alpha.1` and `0.2.1-rc.2` packages
- Startup failure isolation against `0.2.0-rc.2` and `0.2.1-alpha.1`, plus persisted-session restart recovery on `0.2.1-rc.2`
- Conversation mode isolation, cancellation of delayed sends, startup policy checks, settings persistence, cross-tab updates and stale save responses
- Mixed settings APIs, one-time migration, full resets, concurrent edits, crash recovery and failed imports

Runtime tests use controlled agent events and a deterministic model fixture, with no calls to an external model provider

Windows desktop has not been tested directly, and #64 remains open for confirmation from the reporter

## Upgrade

Let active work finish and stop DSH, then update the plugin in the profile you use

```bash
dsh plugin --profile web add dsh-client-auto-continue@0.16.0
dsh web
```

Reload the browser after restarting DSH so it loads the new conversation control

For the desktop app, update from its **Plugins** page and restart the app, since updating the CLI's `web` profile does not update the desktop profile

Existing configuration stays in place, and eligible legacy settings are imported automatically
