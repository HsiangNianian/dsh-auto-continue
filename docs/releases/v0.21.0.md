Restart recovery stops speaking for you: it leaves paused goals alone, doesn't answer questions on your behalf, and respects the retry limit across restarts

All three come from @xiaobaifly7 in [#96](https://github.com/HsiangNianian/dsh-auto-continue/pull/96), found on a real profile

## Paused and blocked goals stay paused

When DSH restarted in the middle of a turn, the plugin sent "continue" without looking at the session's goal. If you had paused the goal, the model took that message as you lifting the pause

Now recovery after a restart or a retryable error skips a session whose goal is **blocked**, or **paused** unless you turned on both **Resume goals** and **Resume paused goals**

- If the plugin can't read the goal, it assumes it's held and doesn't send anything
- This covers live sessions, closed subagents being reopened, and waking the main conversation after a restart
- Finishing a cut-off answer (`max-tokens`, silent turns), the autonomous loop and **Resume now** work the same as before

## A question you haven't answered gets asked again

If the step that got cut off was the model asking you something (`ask_user_question`), "continue" plus the guard note read as your reply. In one case the model kept working for over an hour without the answer it needed

Now the plugin sends a different message in that case, with no guard note: it says the message is automatic, that you haven't answered, and asks the model to ask again and wait

- It's a new setting, **Continue text (unanswered question)** (`continueTextQuestion`), with English, Chinese and Russian defaults. You can edit it like the other continue texts
- A question that timed out normally has a result, so it keeps the usual text

## The retry limit survives restarts

**Max consecutive** (`maxConsecutive`) was only kept in memory, so every restart reset it to zero. A turn that kept crashing the host could go continue → crash → restart → continue forever

Now the startup scan counts the continuations already in the conversation, since your last message, your last stop or the last visible answer, the same way the in-memory count works. Nothing new is written to disk

If **Send continue messages with plugin source** is off, which is the default, continuations look like your own messages. The plugin recognizes them by matching your current continue texts, with placeholders as wildcards. A message you typed that's word for word a continue text counts too, which can only make it stop earlier

I added one change on top: the matching runs in linear time. The first version used a regex that, with a custom template full of placeholders, could take seconds on a long pasted message and stall the startup scan

## Upgrade

Let current work finish, stop DSH, then update the profile you use

```bash
dsh plugin --profile web add dsh-client-auto-continue@0.21.0
dsh web
```

Desktop app users should update through the app's Plugins page and restart the app, since it uses its own profile

- Reload open browser tabs after restarting
- The only new setting is **Continue text (unanswered question)**, which has a default. Nothing else changes

## Validation

- Typecheck, build (committed `lib/` reproduces byte for byte), the full regression suite and the DSH runtime compatibility tests
- New `tests/restart-resume-guards.mjs` (16 cases) covers held goals, paused-goal opt-ins, an unreadable goal, closed subagents, unanswered and timed-out questions, and rebuilding the count from plugin-source and user-source continuations, guard notes, hand-offs and streamed answers. 11 of them fail on 0.20.2
- The linear matcher was fuzzed against the original regex over about 110,000 cases with no differences. A 6 KB near-miss now takes about 2 ms instead of 5.7 s
