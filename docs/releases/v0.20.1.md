A fix for hosts that crash on startup when the profile has a lot of saved sessions

## Startup no longer runs out of memory

Reported and fixed by @anthonyhann in [#91](https://github.com/HsiangNianian/dsh-auto-continue/pull/91)

When DSH starts, the plugin looks through saved sessions for ones that were cut off by the restart. To decide, it read each session's whole log, and only then checked whether the last turn was recent enough to resume (15 minutes by default). On a profile with a few hundred sessions that's gigabytes of decoding. On their machine the host ran out of memory, restarted, tried again, and never came up

Now one start reads at most 32 saved sessions, the most recently active first

- The order comes from DSH's session checkpoint cache, or the session's creation time if there's no cache
- The cache only decides the order. Whether a session gets resumed is still decided by what's at the end of its log, same as before
- A session whose read fails and is retried only counts once
- Sessions past the 32 are skipped. They're the ones that have been idle longest, so they're almost always outside the 15-minute window anyway

Live sessions and subagent sessions aren't affected

## Upgrade

Let current work finish, stop DSH, then update the profile you use

```bash
dsh plugin --profile web add dsh-client-auto-continue@0.20.1
dsh web
```

Desktop app users should update through the app's Plugins page and restart the app, since it uses its own profile

No settings changed

## Validation

- Typecheck, build (committed `lib/` reproduces byte for byte), the full regression suite and the DSH runtime compatibility tests
- New tests cover stopping at 32 reads with the most recently active sessions first, and a few broken logs being retried without pushing healthy sessions out of the budget
- @anthonyhann measured it against a real profile with 903 saved sessions: the 32 most recent hold 3.3 MB of compressed logs, and the six largest logs (7 to 23 MB each) have no checkpoint, sort last, and aren't read at startup

Thanks @anthonyhann for tracking this down with heap numbers instead of just a "it crashes" report
